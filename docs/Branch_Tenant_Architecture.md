# FitCore SaaS — Tenant & Physical Branch Architecture Specification

**Document Version:** 1.0  
**Date:** August 5, 2026  
**Status:** Architecture Specification  

---

## 1. Overview & Hierarchy

FitCore implements a two-tier organization model for fitness businesses:

```
Tenant (Gym Business / Brand Organization)
   │
   ├── Plan Tier Quota Rules (Basic: 1, Pro: 3, Enterprise: Unlimited)
   │
   └── Physical Branches (Physical Locations)
        ├── Main Branch (is_main_branch = true, created at onboarding)
        └── Additional Branches (Created via POST /api/v1/gym/branches)
```

- **Tenant**: Top-level account representing the business (e.g., *Gold Gym India*). Configured in `fitcore_master.tenants`.
- **Physical Branch**: An individual physical gym center/location (e.g., *Gold Gym Downtown*, *Gold Gym Westside*). Configured in `fitcore_shard_*.branches`.

---

## 2. Plan Tier Branch Limits & Enforcement

Physical branch creation is strictly governed by `tenant.plan_tier`:

| Plan Tier | Max Allowed Physical Branches | Behavior when Limit Exceeded |
|---|---|---|
| **Basic** | **1 Branch** (Single Location) | Rejects `POST /branches` with `422 Unprocessable Entity` |
| **Pro** | **3 Branches** | Rejects 4th branch with `422 Unprocessable Entity` |
| **Enterprise** | **Unlimited (999)** | Unrestricted branch creation |

> **Note**: Members and Staff counts are **Unlimited** across all plan tiers.

---

## 3. Branch Authentication & User Context

Users in a Gym Instance log in via `POST /api/v1/gym/auth/login` with `X-Tenant-Slug: <slug>`.

### A. Staff / Trainer / Receptionist Accounts
- Tied to a single specific branch (`staff.branch_id`).
- Upon authentication, their token context locks all UI operations to their assigned branch.

### B. Gym Owner / Admin Accounts (`role: owner`)
- Have access to **ALL** branches within the tenant.
- Operating context:
  - **All Branches View**: Owner sees aggregated metrics across all locations.
  - **Branch-Specific Switcher**: Owner can toggle active branch via `X-Branch-ID: <id>` header in API calls or via frontend navbar selector.

## 4. Data Scoping Architecture Matrix

All data inside tenant shard databases (`fitcore_shard_*`) is partitioned between **Tenant-Level (Global)** and **Branch-Level (Scoped)**:

| Entity | Primary Scope Column | Scoping Behavior & Access Rules |
|---|---|---|
| **Branches** | `tenant_id` | List of all physical locations owned by the tenant. |
| **Membership Plans** | `tenant_id` | **Global**: Configured once per tenant brand. Valid for selection across all branches. |
| **Gym Configurations** | `tenant_id` | **Global**: Tenant logo, tax defaults, notification settings, currency. |
| **Members** | `tenant_id` + `branch_id` | **Scoped**: Assigned to a Home Branch upon onboarding. Cross-branch access checked via membership plan rules. |
| **Staff & Trainers** | `tenant_id` + `branch_id` | **Scoped**: Assigned to a primary working branch location. |
| **Attendance Logs** | `tenant_id` + `branch_id` | **Scoped**: Records exact branch location where member scanned/entered. |
| **Fee Payments & Receipts** | `tenant_id` + `branch_id` | **Scoped**: Tracks revenue generated by individual physical branch locations. |

## 5. Database Schema & Multi-Tenant Model Isolation

### A. `branches` Table Schema (`fitcore_shard_*`)
```sql
CREATE TABLE branches (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    tenant_id VARCHAR(64) NOT NULL,
    name VARCHAR(191) NOT NULL,
    code VARCHAR(64) NOT NULL,
    address TEXT NULL,
    city VARCHAR(100) NULL,
    phone VARCHAR(50) NULL,
    is_main_branch TINYINT(1) DEFAULT 0,
    created_at TIMESTAMP NULL,
    updated_at TIMESTAMP NULL,
    INDEX idx_tenant_id (tenant_id)
);
```

### B. Automatic Multi-Tenant Isolation
All branch and shard models extend `App\Models\Shard\TenantModel`, which enforces:
1. `protected $connection = 'tenant';` (Executes on dynamic DB shard).
2. Global Query Scope `WHERE tenant_id = app('tenant')->tenant_id`.
3. Automatic `tenant_id` assignment upon model instantiation.
